02Findings

Decisive

F1 — Neither candidate isolates any dependency

display/kanban.go:1-13 · display/heatmap.go:1-8 · display/heatmap.templ:1-8

Dependency isolation is the only criterion that has ever justified a sub-module extraction in this repo. Kanban imports utils, utils/svg, and utils/wire — all already universal transitive deps of every consumer. Heatmap imports only utils plus same-package chart_geometry.go (shared nice-max math with BarChart, chart_geometry.go:49,61). A kanban or heatmap module would have the exact dependency footprint consumers already have — a boundary with nothing behind it.

High

F2 — A new module costs 12+ touchpoints, forever

scripts/release.sh · scripts/check-module-sync.sh:18-23 · scripts/check-release-tags.sh · scripts/check-module-layers.sh · .github/workflows/ci.yaml · go.work · visualtest/go.mod · website/go.mod · docs/modularization/README.md · AGENTS.md

Each module is wired into: the release tag set and require-bump sweep, two hardcoded per-module lint/test loops in release.sh (lines 322, 332), the CI lint matrix, GOWORK=off isolation tests, tidy, govulncheck, the module-sync path table, the layers allow-list, workspace use-list, and the require+replace pairs of both in-repo consumers. ADR-0034 explicitly counted this as the negative consequence of the 7-module design. Kanban/heatmap add no isolation win that could pay for it.

High

F3 — Composability payoff: zero evidence

docs/adr/0020-per-package-modules-split.md (trigger criteria) · docs/adr/0039 (22 adopting repos)

Importing a module is not what costs consumers — importing the display package is, and Go compiles at package granularity with the linker pruning unreachable code. No consumer has ever asked for kanban-only or heatmap-only adoption (ADR-0020's demand triggers remain unmet; the 22 known repos adopt the root or icons). A boundary no consumer would import on its own earns nothing.

Gating

F4 — The extraction is a v2-gated breaking change anyway

docs/adr/0039-v2-module-path-timing.md

Moving display.KanbanBoard to a kanban module changes both the import path and the identifier path — a breaking API change. Per ADR-0039, import-path changes ride the v2 module-path migration (option 1: migrate at first real breakage). Extracting now would either break v1 consumers or require a compat shim for a payoff of zero.

Supporting

F5 — Co-change and cohesion evidence

git log display/ since 2026-08-01

93 commits touched display since August; kanban appears in 10 and heatmap in 6 — overwhelmingly their own introduction plus repo-wide sweeps (motion-reduce, dark-mode, lint pins). They are frozen additions, not churn centers. Conversely heatmap is glued to BarChart through chart_geometry; extracting it would force chart_geometry into yet another shared module — precisely the "universal-dependency split" ADR-0034 rejected for utils/svg.

05Trigger Criteria for Future Extraction

Execute a component-family module split when any one fires — the same doctrine as ADR-0020, applied at component granularity:

T1

Unique external dependency

The family needs a dependency no other component uses (precedent: datastar isolating go-datastar/static; errorpage isolating go-error-family).

T2

Documented consumer demand for family-only adoption

A consumer publicly needs the family without the rest of the library (precedent: icons-only adoption driving the icons module).

T3

Family-specific build pipeline or artifact

The family ships its own runtime artifact or build stage (precedent: charts/echarts opt-in adapter; a future WASM or server-driven component runtime would qualify).

If a trigger fires, follow the ADR-0034 mechanics (dual go.work + replace, shared lockstep tags via scripts/release.sh) and time the import-path move with the v2 migration (ADR-0039).
