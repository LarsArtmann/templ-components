00Verdict

The architecture is in the best shape of its series. Every finding from the 2026-05-19 review (B+) that was actionable has since shipped: the htmx → feedback JS-global coupling is gone (feedback owns its dismiss script; feedback/style sharing lives in feedback/styles.go), the AlertType ≡ ToastType duplication was removed at v2-planning (ADR-0022, canonical FeedbackType), inline-script fragmentation was replaced by utils.ScriptComponent with nonce omission semantics, and internal/svg was promoted to the cross-module-safe utils/svg. The 2026-07-18 modularity review's proposed split has since been executed (ADR-0034) and its boundaries re-verified this week by the companion module boundary assessment.

The bottom line Maintain this architecture. No restructuring is warranted; the roadmap below is consolidation and watch items, not repair.

01Structure

Published shape

Layered leaf-kernel: utils (L0, zero internal deps) ← icons, charts/echarts, htmx, datastar (L1) ← errorpage (L2) ← root component packages (L3). Two repo-local modules (visualtest, website) sit outside the published surface. Boundaries are compile-enforced by per-module go.mod files, not conventions.

Scale

137 components across 11 packages, 102 icons, 332 HTML goldens. Root module carries ~80k source lines (display alone ~22k); sub-modules are small and focused (utils 3.4k, icons 1.6k, errorpage 3.9k, htmx 1.3k, datastar 1.8k, echarts 0.4k). Test code roughly equals source at every level.

04Pain points

display: one package, 53 components

27 hand-written source files, ~22k lines, charts and overlays and tables in one namespace. Change ripple inside the package is contained (Go package-level compile), but code review surface and merge-collision odds grow with every component. This is the only under-modularized spot in the workspace — and its resolution is decided policy: ADR-0040 trigger-gates any extraction to v2 (T1 unique dependency / T2 consumer demand / T3 own build pipeline). None has fired. The correct action is monitoring, not splitting.

Per-component ceremony

Adding one component touches: the .templ source, generated output, goldens, demo page registration, FEATURES/SKILL count tables (machine-guarded), and the tc mirror. The guards make the ceremony impossible to skip — which is the point — but the count upkeep is manual. A count-codegen (derive the tables from the same build.CountStats the website uses) would delete a recurring friction class. Effort S/M, no consumer impact.

templ version gate (external)

templ ≥ v0.3.1100 deleted templ.ResolveAttributeValue; the pinned v0.3.1020 generator and forward-compat consumers constrain the window. #368/#369 are deliberately bundled into the same one-event re-baseline. This is an external constraint with an internal probe (scripts/check-templ-gate.sh) — watch, don't fix.

What we did not find

No dead modules (every module has in-repo consumers plus the published surface), no orphaned packages (cmd/tc is the adoption-inspection tool), no testing pain from coupling (every module tests green in isolation with GOWORK=off), and the error modernization sweep found zero legacy errors.As/errors.Is findings repo-wide.
