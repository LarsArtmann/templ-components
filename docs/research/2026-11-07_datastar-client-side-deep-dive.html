Datastar on the Client: What templ-components Hasn't Used Yet

The library integrated Datastar well as a transport — wire, LiveRegion, SSE error handling. This report maps the client-side capabilities of the pinned runtime that the library has not touched, verifies each one against the sha-pinned bundle bytes, and ranks eight concrete improvement opportunities.

00Summary

The headline finding: the pinned Datastar 1.0.3 runtime ships an opt-in CSP mode that removes the 'unsafe-eval' requirement — and the library doesn't use it. Today every Datastar page in this library and its demo demands script-src 'unsafe-eval' because data-attribute expressions compile through the Function() constructor. The pinned bundle instead reads data-nonce="…" from the <html> element and, when present, executes expressions as nonce'd inline scripts (with a Trusted Types policy when the browser offers one). Adopting it is a library-level plumbing change in layout plus a demo/website CSP tightening — no version bump required, and it aligns the library with the strict-CSP posture its own docs sell.

Behind that headline sit two more structural gaps. First, the library treats Datastar purely as an element-patching transport: nothing consumes datastar-patch-signals, reactive bindings (data-text, data-show, data-on-signal-patch), or the fetch options (headers, payload, filterSignals, openWhenHidden) that are all byte-present in the pinned runtime. Second, half of the planned Tier-B surface from the 2026-08 adoption analysis — typed builders for the reactive markup attributes — was never built, so consumers who want client-side reactive state have no typed, fuzz-tested API and fall back to raw string attributes.

The bottom line Nothing here argues for replacing HTMX or re-litigating ADR-0030's transport decision — the decision ladder stands. The opportunities are: (1) make the Datastar pages we already ship strict-CSP-clean, (2) expose the runtime's signal channel as a first-class, documented pattern, and (3) finish the typed API surface so client-side reactivity is as safe as the transport side already is. Upstream v1.0.4 adds no breaking changes; its requestCancellation race fix is a direct LiveRegion benefit and should be folded into the next scheduled pin bump.

02Pinned-bundle evidence (verified today)

Method: grepped the sha-pinned bundle ($(go env GOMODCACHE)/github.com/larsartmann/go-datastar/static@v0.6.1/datastar.js, 33,538 bytes) for capability tokens. The CSP-mode decode (the load-bearing one)

From the pinned bytes, the activation and execution path is: 

wt = "data-nonce"
tt = documentElement.getAttribute("data-nonce")   // read once at init
nt = tt !== null                                  // CSP mode if attribute exists
if (nt) {
  if (!tt) throw "Datastar CSP requires a nonempty html data-nonce."
  Mt.removeAttribute(wt)                          // attribute is stripped from the DOM
  ve = window.trustedTypes?.createPolicy("datastar",
        { createHTML: e => e, createScript: e => e })
}
// every runtime-created script:
Ee = (el, code) => { if (nt) el.nonce = tt; el.text = ve ? ve.createScript(code) : code }

Reading: with data-nonce="<page nonce>" on <html>, the runtime stops compiling expressions via Function() and instead executes them as inline scripts carrying the page's nonce — which a script-src 'nonce-…' CSP allows without 'unsafe-eval'. An empty data-nonce attribute throws at init (loud, not silent). When Trusted Types are enforced, the runtime self-registers a permissive datastar policy (identity functions) — worth knowing in a require-trusted-types-for 'script' audit. CSP mode changes the script-creation mechanism, not the plugin set; no feature gate is visible in this path. Two honest caveats for adoption: nonce'd-script execution has a different (plausibly higher) evaluation cost than eval, and the library's exact attribute set (data-init, data-on:* + __debounce modifiers, data-on-interval, data-on-intersect, data-indicator, data-show) must be browser-proven under CSP mode before the docs flip — the repo's own e2e harness (visualtest/datastar_runtime_e2e_test.go) is the tool. 

// The fetch-options destructure, minified, verbatim from the pin:
json, filterSignals: { include: /.*/, exclude: /(^|\.)_/ } = {},
openWhenHidden: w = n /* per-action default: off for @get, on otherwise */,
payload: y, requestCancellation: A = "auto",
retry: d = "auto", retryInterval: h = 1e3, ...

Note filterSignals' default: local signals whose names contain a _ segment ((^|\.)_) are excluded from the request body — the runtime's built-in local/backend signal split, relevant to any future wire SignalsFilter modeling.

03Opportunities, ranked

Eight opportunities, ordered by impact. The first four are the substance; five through eight are small or deliberately deferred. None re-litigates the transport decision (ADR-0030) or the JS decision ladder: HTMX stays the default; Datastar stays opt-in.

Opportunity 1 · High impact · Medium effort · Do first

Adopt CSP mode: drop 'unsafe-eval' from every Datastar page

layout.Base/Minimal + DefaultPageProps (attribute goes on <html>) · examples/demo + website/firebase.json CSP headers · docs/datastar-runtime-facts.md §CSP

Today 'unsafe-eval' rides every Datastar CSP — demo (withSecurityHeaders), the pinned firebase.json /demo/** header override, and every consumer following the runtime-facts page. That token defeats the strict-CSP posture the library sells ("CSP-safe by construction") and is the single most-exploited CSP weakness in the modern guidance (strict target: script-src 'nonce-…' 'strict-dynamic' with no eval token). The pinned runtime already ships the answer: put data-nonce="<same nonce>" on <html> and expressions execute as nonce'd inline scripts. 

// Target surface (illustrative):
@layout.Base(layout.DefaultPageProps())   // today: no data-nonce anywhere

// proposal: a single opt-in field on the page props
layout.DefaultPageProps()                 // unchanged, htmx pages untouched
props.DatastarNonce = demoNonce           // Base renders <html data-nonce=...>
// consumers pair it with:
@datastar.SDKScript(datastar.SDKScriptProps{Nonce: demoNonce})

Design notes. The attribute must sit on the <html> element — layout is the only module that renders it, which makes this a PageProps/BaseProps-adjacent field, not an SDKScript prop (the script tag cannot carry it). The runtime strips the attribute at init, so goldens will see it in server HTML — a golden update, not a problem. Value and script nonce must be the same nonce; document the pairing loudly, because a mismatched value silently fails the CSP (or throws if empty). htmx pages are untouched: the field is opt-in and inert without the Datastar runtime.

Fix path (1) e2e spike: run the existing Datastar e2e suite against a CSP-mode page (nonce + no 'unsafe-eval') and verify every attribute the library emits still fires — including __debounce modifiers and the SSE error handler. (2) Plumb the field through layout with goldens. (3) Flip the demo's withSecurityHeaders and the firebase.json override in the same commit (the two must stay equal by rule), regenerate the site CSP via go run ./cmd/site --update-csp. (4) Correct the runtime-facts §CSP section to "eval by default; CSP mode via data-nonce, bundle-verified at the pin" and add the data-nonce token to TestPinnedRuntimeBundleContract so a bump that drops the mechanism fails CI.
Opportunity 2 · High impact · Medium effort

Signal-only live data: use the datastar-patch-signals channel the runtime already speaks

datastar.LiveRegion (element-patching only today) · new docs/recipes/datastar-signals-live-data.md · demo

Every Datastar streaming path in the repo patches elements: LiveRegion docs and the demo stream datastar-patch-elements events with rendered HTML. The pinned runtime also speaks the signals channel: datastar-patch-signals SSE events (with onlyIfMissing), consumed reactively by data-text/data-show bindings and the data-on-signal-patch plugin — all byte-present at the pin, none modeled. For dashboard-shaped pages (this library's stated #1 use case), the difference is structural: an element patch re-renders and re-ships HTML on every tick; a signal patch ships a few JSON bytes and the client re-renders the bound nodes itself. 

// Target pattern (recipe-shaped, not a new component family):
@datastar.LiveRegion(datastar.LiveRegionProps{URL: "/stream/metrics", ...}) {
    @display.StatCard(display.StatCardProps{
        BaseProps: utils.BaseProps{ID: "users"},
        Label:     "Active users",
    })   // StatCard's value node carries data-text="$metrics.users"
}
// server: PatchSignals({"metrics.users": 1241}) over the same stream

Why a recipe first, not a component: the binding lives on a child element the consumer composes (StatCard has no signal-aware slot yet), and the server side is go-datastar SDK territory (consumer go.mod). The recipe becomes the Datastar twin of docs/recipes/sse-live-rows.md (the htmx SSE-append pattern, shipped for #344) and reuses the existing wire framing: response-driven, id-matched patches stay the element path; signal patches are the additive channel. filterSignals' (^|\.)_ local-signal exclusion (verified above) is the doc footnote that keeps mixed local/backend state sane. A demo card proves it in a browser; a future SignalRegion-flavored component (or a signal-aware StatCard slot) is a follow-on only if the recipe shows demand.

Why it matters This is Datastar's genuine differentiator over htmx (which has no client-side state at all), and it maps onto the component the library already leads with for "dashboard / metrics page". Today the library documents the element channel only — a consumer reading our docs would never learn the cheaper channel exists.
Opportunity 3 · High impact · Medium-high effort

Build the typed reactive attribute builders — the unbuilt half of Tier B

datastar/ module (new attributes.go) · planned 2026-08-02 in docs/research/datastar-integration-analysis.md §Tier B, never shipped

The August plan sketched datastar.Text, datastar.Bind, datastar.Show, datastar.Signals, datastar.Computed returning templ.Attributes. What shipped is the transport half only: five action-expression helpers (datastar/indicator.go:53-107) and the six components. The gap shows: consumers who follow the demo's lead (data-on:click={ datastar.Post(url) }) have no typed path for the reactive half and hand-write raw strings — exactly the surface where this library's value (escaping, validation, graceful degradation) should live. 

// Target API (matching the repo's conventions):
datastar.Show("$open")                       // data-show="$open"
datastar.Text("$metrics.users")              // data-text="..."
datastar.Bind("query")                       // data-bind:query
datastar.Signals(map[string]any{"open": false}) // data-signals={JSON}
datastar.Computed("total", "$price * $qty")  // data-computed:total
datastar.On("keyup", expr).Debounce(300)     // data-on:keyup__debounce.300ms

Safety rules the implementation must carry (each has precedent in the repo): expressions are code, so every builder either validates or escapes — the action helpers' single-quote escaping (fuzz-proven by FuzzActionExpr) extends to all expression-typed arguments; signal names get an identifier grammar (dotted paths, _-local prefix) with an IsValid()-style guard, matching the every-enum-ships-its-test rule; JSON payloads go through templ.JSONString (the Alpine precedent in the JS guide); and the FilterInput design note's rule stands — no URL string-concatenation helpers, the injection-surface rejection is on record in docs/transport-wiring.md. Degrade empty to nothing, never to something wrong. Goldens + the golden sweep table cover every builder; wire's dialect-contract reflection test (TestEveryActionFieldHasADialectContract) is the model for keeping the builder set exhaustive against the runtime plugin list.

Opportunity 4 · Medium impact · Medium effort

Model the verified fetch options on wire.Action: Headers, Payload, SignalsFilter, OpenWhenHidden

utils/wire (Action struct + datastarAttributes) · dialect contract: TestEveryActionFieldHasADialectContract (invariants_test.go:517)

The pinned destructure accepts four options wire never emits: headers (custom request headers — htmx twin: hx-headers), payload (explicit request body overriding signal serialization — nearest htmx twin: hx-vals; asymmetric), filterSignals (send a signal subset — nearest twin: hx-params; asymmetric), and openWhenHidden (keep fetching while the tab is hidden; off by default for @get — the action both LiveRegion and PolledRegion use — on for the write actions; no htmx twin; htmx always polls). Each is a small field plus one dialect-mapping row — and each is exactly the kind of runtime fact this repo prefers owned by typed fields instead of consumer folklore.

OpenWhenHidden is the interesting one: Datastar's default (skip fetch work in hidden tabs) is right for battery, wrong for audit-tail/monitoring regions a consumer deliberately runs in the background — today there is no way to express that choice through the library. The LiveRegion/PolledRegion props are the natural ride-along surface for the same option. The wire dialect-contract guard makes this addition mechanical: every new field needs its htmx/Datastar row stated (render, ignore, or degrade) in the reflection test, or CI fails — the guard that caught the orphan __debounce bug in #331.

Opportunity 5 · Medium impact · Low-medium effort · Own event

Bump the pin to v1.0.4 at the next scheduled window

datastar go.mod + docs/datastar-runtime-facts.md re-audit + datastar/bundle_guard_test.go + docs/external-dependency-bumps.md protocol

No urgency — zero known 1.0.3 defects in the paths the library uses — but the delta includes one fix the library's own godoc recommends into exactly the affected area: requestCancellation: 'cleanup' no longer dispatches after the initiating element is removed, and a superseded request can no longer remove its replacement's cleanup (#1205). LiveRegion.CancellationCleanup (the swap-replaced region pattern) inherits both. The bump also unlocks @query(), the data-star-nonce CSP alias, and the expression-rewriting fix for action calls inside string literals. Bundle bytes will change, so this is a full verify-at-source event per docs/external-dependency-bumps.md: diff old/new, re-audit every runtime-facts claim (this report's token table is the checklist), update pinnedBundleSHA256, warm [Unreleased]. Fold it into the window after Opportunity 1 lands so the CSP-mode re-audit runs once, not twice.

Opportunity 6 · Low-medium impact · Low effort · Verify first

Consider modeling viewTransitionSelector (per-element View Transitions)

utils/wire/handler.go PatchTarget · sibling dataline to the modeled useViewTransition

The dataline is byte-present at the pin and unmodeled: wire stamps only the boolean Datastar-Use-View-Transition header. The repo's own finding (runtime-facts, 2026-10-03) is that the non-SSE HTML converter maps kebab-cased dataline names 1:1 to response headers, and its namespace sibling rides the same converter — so Datastar-View-Transition-Selector plausibly works the same way. Plausibly is not proven: the kebab forms are computed, not literals, so grep cannot settle it. One browser probe settles it; if it lands, PatchTarget.ViewTransitionSelector gives per-element transition scoping (animate only the swapped card, not the page) that htmx cannot express per-swap at all.

Opportunity 8 · Low impact · Low effort · With Opportunity 3

One reactive client-state demo card — and an explicit non-goal note

examples/demo/datastar_demo.templ · docs/javascript-guide.md

The demo teaches both transports for transport patterns but never shows the rung-7 differentiator: declarative client-side state. One card (tabs or a visibility toggle driven by data-signals + data-show through the new builders) closes that. The same section should carry the non-goal in writing: components that already work on native HTML (<details>, Popover API, <dialog>) and singleton scripts stay native-first — no Datastar twins of Combobox/Tabs/Carousel just because signals could express them. The August analysis' "replace the singleton scripts with signals" idea (its C2/C3) reads today as a ladder violation, not an opportunity; the reactive builders exist for consumers' own glue, not for re-porting the library.
