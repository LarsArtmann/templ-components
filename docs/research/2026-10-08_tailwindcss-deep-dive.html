00Summary

templ-components treats Tailwind v4 as infrastructure, not as a styling afterthought. The CSS-first configuration model is adopted end to end: @import "tailwindcss" source(none) with an explicit @source allowlist that scans both .templ and .go files — solving the lookup-maps-live-in-Go blind spot that silently drops classes in most Tailwind projects, and guarding it with a dedicated test. Class-strategy dark mode, container queries, logical properties, and motion-reduce fallbacks are not just used, they are enforced by eight repo-wide guard tests. The compiled demo artifact is built with v4.3.3 — the latest release.

The gaps are narrow and specific. One finding rises above hygiene: a dozen hardcoded palette literals in custom.css bypass the CSS-variable theming model that is the library’s own headline promise. The rest are modernizations against features Tailwind shipped after the affected code was written: scrollbar-none, field-sizing-content, user-valid:/user-invalid:, the inset-s-*/inset-e-* rename that deprecates the repo’s canonical start-*/end-* RTL pattern, and @utility tree-shaking for the .tc-* classes.

The bottom line This is one of the most disciplined Tailwind v4 codebases auditable from the outside — framework conventions are enforced by tests, not comments. The single action with real consumer impact: replace the 12 hardcoded hex/rgb palette literals in templates/custom.css with var(--color-*) references so a consumer’s @theme override actually re-skins checkboxes, validation borders, and kanban indicators — today it silently does not.

01Findings

Feature-by-feature assessment, ordered by impact. Every claim cites repo source (file:line) and the Tailwind capability (docs/release source).

Misused · Breaks the theming contract

Hardcoded palette literals in custom.css bypass the @theme theming model

templates/custom.css:324,330 (accent-color rgb(37 99 235) / rgb(96 165 250)) · :341-348 (user-valid/invalid rgb(220 38 38) / rgb(22 163 74)) · :1045-1063 (kanban #2563eb, #93c5fd, #dc2626, #f87171, #1e3a8a) · :972-977 (--ds-brand) — 12 hex/rgb lines, zero uses of --alpha()

The library’s documented promise (README, skill, ADR-0008): consumers re-skin every component globally via @theme { --color-blue-600: ... } with no Go changes, because components emit standard Tailwind utilities that resolve through theme variables. The hand-written .tc-* CSS does not honor that promise: native form-control accent color, CSS-only validation borders, and all kanban drag/pending/fail indicators are literal palette values. A consumer remapping blue-600 to indigo gets a half-themed app — checkboxes, progress bars, and kanban states stay stock Tailwind blue/red with no error pointing at the cause. The repo already proved the correct pattern in-house: the sidebar chrome is theme-adaptive via --tc-sidebar-* tokens that reference var(--color-gray-*) (custom.css:516-535). 

/* Before — custom.css:324 (immune to @theme overrides) */
accent-color: rgb(37 99 235); /* blue-600 */

/* After — resolves through the consumer's @theme */
accent-color: var(--color-blue-600);

/* Translucency without hex-alpha literals (v4 function, docs:
   tailwindcss.com/docs/functions-and-directives) */
border-color: --alpha(var(--color-blue-500) / 30%);
Recommendation Replace all 12 literals with var(--color-*) references and adopt --alpha() for the translucent hex suffixes. Then extend the guard family: a TestCustomCSSThemeTokens scan that fails on raw hex/rgb color values in custom.css (comment-ignored), mirroring TestDarkModeCompliance. Impact is immediate and consumer-visible; effort is one file.
Partially Used · Deprecation exposure

start-*/end-* are deprecated since v4.2 — the repo’s RTL canon needs the inset-s-*/inset-e-* rename

11 sites across 7 files: errorpage/notfound404.templ:119 · feedback/toast.templ:92 · forms/toggle.templ:102 · forms/input_group.templ:60,68 · display/avatar.templ:108,136 · display/carousel.templ:86,96 · display/hover_card.templ:19-20 · AGENTS.md RTL convention · utils.TestRTLLogicalProperties pins the old names

Tailwind v4.2.0 introduced inset-s-*/inset-e-* as the canonical logical inset utilities and deprecated start-*/end-* (the v4.2.3 release notes ship the upgrade-tool migration for exactly this rename; source: GitHub releases, v4.2.0/v4.2.3 entries). The old names still compile today, so nothing is broken — but they sit inside the repo’s most load-bearing convention: absolute positioning of tooltips, carousel arrows, toggle thumbs, avatar status dots, and the toast container. If the aliases are ever removed, every one of those loses RTL mirroring silently in production. Zero inset-s-/inset-e- uses exist today; the guard test actively canonizes the deprecated form. 

<!-- Before: display/carousel.templ:86 -->
class="absolute start-0 top-1/2 ..."

<!-- After: same box, canonical v4.2+ logical inset -->
class="absolute inset-s-0 top-1/2 ..."
Recommendation Mechanical 21-site rename plus updates to the RTL section of AGENTS.md, the skill, and utils.TestRTLLogicalProperties (which should ban start-/end- going forward). Safe, purely positional, goldens verify.
Partially Used · Drift risk

CSS build lanes are version-unpinned outside nix — today aligned, tomorrow divergent

.github/workflows/website.yml:68 (npm install --no-save tailwindcss @tailwindcss/cli) · examples/demo/Dockerfile:18 (pnpm add tailwindcss @tailwindcss/cli) · flake.nix:75 (nixpkgs tailwindcss_4 = 4.3.3)

Three lanes compile this library’s CSS: the nix dev shell (builds the committed artifacts, currently 4.3.3), the website CI job (installs latest at run time), and the demo Docker build (installs latest at build time). Today all three agree because 4.3.3 is the newest release. The moment 4.4.0 ships, Docker and website rebuilds silently compile with a different generator than the committed artifacts were built with — the exact drift class this repo already paid for once with the templ v0.3.1020 generator pin (a system binary produced cosmetic diffs across 51 generated files). TestCSSFreshness catches staleness, not version skew. 

# Before — examples/demo/Dockerfile:18 (floating)
RUN pnpm add tailwindcss @tailwindcss/cli

# After — pinned, bumped deliberately in the same commit as flake.nix
RUN pnpm add tailwindcss@4.3.3 @tailwindcss/cli@4.3.3
Recommendation Pin an explicit version in both unpinned lanes and add the bump to the same deliberate-commit ritual as the templ pin. Low effort now; prevents a confusing “CSS changed without a source change” incident later.
Partially Used · Consumer bundle size

.tc-* utility classes ship unconditionally — @utility would make them tree-shakeable

templates/custom.css (14 plain .tc-* classes in @layer utilities, ~1,091 lines imported wholesale) · @utility used exactly once: templates/presets/glass.css:35

Tailwind v4’s @utility directive defines first-class utilities that are only emitted when the content scanner sees them used, and that compose with variants (hover:, dark:, md:). Plain classes inside @layer utilities of an imported file ship to every consumer regardless of use, and cannot take variants. Because every consumer imports custom.css via app.css, an icons-only or three-component adoption still ships all 14 .tc-* classes (overlay transitions, select styling, kanban states, animations, scroll-snap, fluid typography). Verified: zero variant-prefixed tc-* usages exist, so today the win is dead-CSS elimination for minimal-adoption consumers — the adoption mode this library explicitly documents (docs/icons-only-adoption.md) — not variant composability. 

/* Before — always emitted */
@layer utilities { .tc-squircle { corner-shape: squircle; } }

/* After — emitted only when a scanned class uses it */
@utility tc-squircle { corner-shape: squircle; }
Recommendation Migrate only utility-shaped classes (tc-squircle, tc-content-auto(-compact), tc-no-scrollbar, tc-auto-grow, tc-snap-*, tc-fluid-*); keep component-shaped CSS (tc-select, tc-modal, tc-drawer, tc-log, tc-kanban, tc-anim-*) as plain classes since they need selectors, pseudo-elements, and @supports blocks. Sync TestCustomCSSUtilities. Re-baseline goldens and visuals — schedule with the next planned one, not ad hoc.
Missed Opportunity · Low impact

.tc-no-scrollbar duplicates v4.3’s scrollbar utilities

templates/custom.css (.tc-no-scrollbar + ::-webkit-scrollbar rules) · display/carousel.templ:64

v4.3.0 shipped native scrollbar utilities: scrollbar-{auto,thin, none} plus scrollbar-thumb-*/scrollbar-track-*>> /scrollbar-gutter-* (source: GitHub releases, v4.3.0). The hand-rolled .tc-no-scrollbar predates that and is now a duplicate of scrollbar-none. 

<!-- Before: display/carousel.templ:64 -->
class="flex overflow-x-auto snap-x snap-mandatory scroll-smooth tc-no-scrollbar"

<!-- After -->
class="flex overflow-x-auto snap-x snap-mandatory scroll-smooth scrollbar-none"
Recommendation Swap the class, delete the custom rule, update TestCustomCSSUtilities. Two-file change.
Partially Used · Low impact

Hand-rolled CSS now covered by v4 built-ins: field-sizing and user-valid

templates/custom.css (.tc-auto-grow: field-sizing: content + min/max-height) · templates/custom.css:337-349 (user-valid/user-invalid border defaults)

Two more custom.css blocks duplicate utilities Tailwind now ships: field-sizing-content exists since v4.0 (tailwindcss.com/docs/field-sizing) and would let forms.Textarea emit field-sizing-content min-h-10 max-h-80 instead of the .tc-auto-grow class; user-valid:/ user-invalid: variants exist since v4.1 (tailwindcss.com/docs/hover-focus-and-other-states) and could express per-component validation styling. One honest counterpoint: as a global default, the base-layer rule for validation borders is a defensible layer choice — the real defect there is the hardcoded palette, already covered by finding 1. Keeping .tc-auto-grow as a single guarded point of truth is also defensible; if kept, its comment should say so explicitly.

Recommendation Adopt field-sizing-content in the Textarea component and retire .tc-auto-grow; treat user-valid/invalid as a docs-level note (variants available) rather than a migration.
Missed Opportunity · Low impact

size-* never used — 168 collapsible w-N h-N pairs

w-5 h-5 ×68 · w-4 h-4 ×40 · w-6 h-6 ×38 · w-12 h-12 ×8 · w-3/8/9/10/16 pairs ×14 — icon boxes, avatars, status dots, kanban handles across display/forms/feedback

Tailwind v4’s size-N (v4.0) collapses same-value width + height into one token, and v4.2.2’s canonicalizer even collapses the pair in output CSS. The codebase has 168 sites writing the pair the v3 way. Rendered output is visually identical either way; this is code economy and idiom, not correctness. 

<!-- Before -->
class="h-5 w-5 shrink-0"

<!-- After -->
class="size-5 shrink-0"
Recommendation Mechanical sweep — but it touches many goldens. Bundle it with the next planned visual/golden re-baseline (e.g. the templ v0.3.1070 generator migration already queued in TODO_LIST) rather than spending an isolated re-baseline on it.
Partially Used · Cosmetic

bg-gradient-to-* legacy aliases in the one gradient usage

errorpage/notfound404.templ:42 (hero numeral gradient, 2 tokens incl. dark: variants) · website/internal/pages/hero.templ:107

Tailwind v4 renamed gradient utilities to bg-linear-to-*; the v3-era bg-gradient-to-* names remain as deprecated aliases that still compile. The repo uses the legacy form at its only two gradient sites. Nothing breaks today; the canonical name is future-proof. 

<!-- errorpage/notfound404.templ:42 -->
bg-gradient-to-br from-blue-600 via-blue-500 to-indigo-500
<!-- becomes -->
bg-linear-to-br from-blue-600 via-blue-500 to-indigo-500
Recommendation Two-line rename; fold into any pass through errorpage or the website hero.

05Conclusion

templ-components uses Tailwind v4 about as well as a Go server-rendered library can: CSS-first config adopted to the letter, the one Tailwind feature this codebase uniquely needs (scanning Go source for class maps) implemented and test-guarded, accessibility and RTL conventions enforced by machine, and the generator current at 4.3.3. The adoption score of 82 rests on one real violation — hardcoded palette literals in custom.css that quietly break the library’s own @theme re-skinning promise — plus a short, mostly mechanical list of v4.2/4.3 modernizations. Fix finding 1 in an afternoon, fold findings 2-8 into already-planned re-baselines, and this codebase is a reference implementation.
