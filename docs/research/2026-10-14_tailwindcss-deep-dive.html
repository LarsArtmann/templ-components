00Summary

templ-components treats Tailwind v4 as load-bearing infrastructure, and the discipline is enforced by tests rather than convention documents: curated @source scanning that covers Go-embedded class maps, a class-strategy dark mode scanned line-by-line, motion-reduce fallbacks counted per utility, and a CSS build pipeline with freshness and inventory guards. The pinned generator — 4.3.3 in all three build lanes — is still the newest release as of 2026-10-14, so there is zero version debt to pay.

Since the first audit (2026-10-08, score 82), five findings were remediated and are verified fixed in this tree: the hardcoded palette literals in custom.css (now var(--color-*) + --alpha(), guarded by TestCustomCSSThemeTokens), the deprecated start-*/end-* insets (now the v4.2-canonical inset-s-*/inset-e-*, with the guard test banning the old names), the unpinned CSS build lanes (now lockstep-pinned at 4.3.3), .tc-no-scrollbar (replaced by v4.3's scrollbar-none), and the legacy bg-gradient-to-* aliases (now bg-linear-to-*). That remediation pace is the story of this audit: the findings list below is narrower and deeper than last time.

The bottom line The library's own CSS now honors its theming contract; the next unit of value is consumer-facing composability. Three moves deliver most of it: (1) adopt @variant dark { } inside custom.css to delete the ~15 hand-written .dark selector blocks, (2) convert the simple .tc-* helpers to @utility so consumers get tree-shaking and hover:tc-*-style variant composition, and (3) replace the website's WebKit-only hand-rolled scrollbar CSS with v4.3's cross-browser scrollbar-* utilities.

02Findings

Ordered by impact. New findings from this audit are marked NEW; items carried from the prior audit are marked CARRIED.

Partially used · High impact · NEW

@variant unused in custom.css — every dark-mode rule is a hand-written .dark selector fork

templates/custom.css:429-460 (select + picker dark blocks), :294-328 (base layer), :1074+ (coarse pointer) · docs: tailwindcss.com/docs/functions-and-directives

custom.css is compiled by Tailwind (imported by app.css and demo.css), so the @custom-variant dark defined in app.css:48 is in scope — but the file never uses it. Instead, the stylable select alone duplicates its light-mode rules under a .dark prefix eight times (background, border, focus ring, picker icon, picker panel, options…), and v4.3's stacked (@variant hover:focus) and compound (@variant hover, focus) forms — verified against the official docs — would let hover/focus/dark combinations collapse into single blocks. Each hand-written fork is a place a future edit can forget the dark half. 

/* Before — two rules per property, drift-prone (custom.css:429) */
select.tc-select { background-color: var(--color-white); }
.dark select.tc-select { background-color: var(--color-gray-900); }

/* After — one rule, variant-nested (v4.3 compound syntax) */
select.tc-select {
  background-color: var(--color-white);
  @variant dark { background-color: var(--color-gray-900); }
  &:focus-visible {
    box-shadow: 0 0 0 2px --alpha(var(--color-blue-500) / 30%);
    @variant dark {
      box-shadow: 0 0 0 2px --alpha(var(--color-blue-400) / 30%);
    }
  }
}
Recommendation Migrate the .dark forks in the select block (and the backdrop/overlay color swaps) to @variant dark { }. Output CSS is semantically identical, so goldens verify without a visual re-baseline; TestCustomCSSUtilities still passes since class names are unchanged.
Partially used · High impact · CARRIED

Simple .tc-* helpers still ship in @layer utilities — no tree-shaking, no variants

templates/custom.css (14 plain classes, ~1,091 lines imported wholesale) · used once ever: templates/presets/glass.css:35 · docs: tailwindcss.com/docs/utility-directive

Verified rules of @utility: classes registered with it are emitted only when the scanner sees them used, and they compose with every variant (hover:, dark:, md:). Plain classes in @layer utilities of an imported file ship to every consumer regardless of use and cannot take variants. Because app.css imports custom.css unconditionally, an icons-only or three-component adoption still ships all fluid typography, scroll-snap, content-visibility, and squircle CSS. The constraint that kept this open is real: compound selectors (dialog.tc-overlay, the @supports select block) cannot be @utility — but that was never the proposal. 

/* Before — always emitted, variant-deaf */
@layer utilities {
  .tc-content-auto { content-visibility: auto; contain-intrinsic-size: auto 48px; }
}

/* After — tree-shaken, composable: <div class="hover:tc-content-auto"> */
@utility tc-content-auto {
  content-visibility: auto;
  contain-intrinsic-size: auto 48px;
}
Recommendation Convert only utility-shaped single-class rules: tc-content-auto(-compact), tc-auto-grow, tc-squircle, tc-snap-*, tc-fluid-*. Keep component-shaped CSS (tc-select, tc-modal, tc-log, tc-anim-*) as-is. Layer re-sorting means this needs the next planned golden/visual re-baseline, not an ad-hoc run. Sync TestCustomCSSUtilities.
Missed opportunity · Medium-high impact · NEW

The website hand-rolls WebKit-only scrollbar CSS — v4.3's scrollbar-* utilities cover all engines

website/site.css:223-237 (::-webkit-scrollbar, -track, -thumb, -thumb:hover) · docs: v4.3.0 release notes

The library already proved the migration inside its own components (carousel's scrollbar-none), but the website's own chrome still styles scrollbars through ::-webkit-scrollbar pseudo-elements — which Firefox ignores entirely, so Firefox visitors get default fat scrollbars on every docs page. v4.3.0 shipped scrollbar-{auto,thin,none}, scrollbar-thumb-*, scrollbar-track-*, and scrollbar-gutter-*, compiling to the standard scrollbar-width/scrollbar-color properties with the WebKit fallback included. 

<!-- Before — site.css:223-237 + scattered usage; Firefox sees none of it -->
::-webkit-scrollbar { height: 6px; } ::-webkit-scrollbar-thumb { background: ...; }

<!-- After — one utility chain, all engines, dark: aware -->
<div class="scrollbar-thin scrollbar-thumb-gray-300 dark:scrollbar-thumb-gray-700">
Recommendation Replace the ::-webkit-scrollbar block with utilities on the scrolling containers, and while there, refresh docs/tailwind-v4-adoption-guide.md:89-94 — its "manual setup" example still teaches a hand-rolled .scrollbar-thin utility that Tailwind now ships natively. Docs teaching hand-rolls for shipped utilities is the cheapest possible drift to fix.

Missed opportunity · Medium impact · NEW

Zero aria-* variants — state styling routes through JS-set data attributes instead

0 uses repo-wide (counted) · contrast: display/command_palette.templ (5 data-[tc-palette-active=true]: sites), forms/combobox.templ (data-[selected]:) · docs: tailwindcss.com/docs/hover-focus-and-other-states

Tailwind ships nine built-in aria-* variants (aria-checked, aria-selected, aria-expanded, aria-disabled…) plus arbitrary aria-[sort=ascending]: and composable group-aria-*/peer-aria-*. The components already maintain these ARIA attributes for accessibility — but style from parallel JS-managed data-* hooks instead. Where an element's aria state flips with its visual state (tabs: aria-selected, dropdown triggers: aria-expanded, combobox options: aria-selected), the aria variant can replace a JS class mutation, shrinking the singleton scripts. 

<!-- Tab trigger — style follows the ARIA state it already sets -->
<button role="tab" aria-selected="true"
        class="aria-selected:border-blue-600 aria-selected:text-blue-600 ...">

<!-- Dropdown trigger — chevron rotates with aria-expanded, no JS class writes -->
<button aria-expanded="false" class="aria-expanded:rotate-180 transition-transform">
Recommendation Adopt for new components first (Tabs refactors, Dropdown trigger rotation), keeping the existing data-* machinery until each component's next natural touch. Golden churn is per-component, so this rides the ordinary workflow rather than a dedicated sweep.
Missed opportunity · Medium impact · NEW

The 11 icon animations live outside the theme — consumers can't compose them with variants

templates/custom.css:659-930 (tc-anim wrapper + 11 tc-icon-* keyframes) · icons.AnimatedIcon · docs: tailwindcss.com/docs/theme (animate namespace)

@theme's --animate-* namespace turns a keyframe into a first-class animate-* utility that composes with every variant. Today the animations are reachable only through the tc-anim-* wrapper classes, which hard-code the hover/focus trigger — a consumer wanting "pulse on group hover" or "spin while pending" (kanban already ships its own tc-kanban-pending-spin keyframe for exactly this) must write new CSS. Registering the same keyframes as theme tokens adds zero runtime and opens the full variant surface; the reduced-motion story stays with the existing motion-reduce:animate-none convention the repo already guards. 

@theme {
  --animate-tc-pulse: tc-icon-pulse 0.9s ease-in-out;
  /* keyframes live inside @theme, emitted only when used */
  @keyframes tc-icon-pulse { 0%, 100% { scale: 1; } 50% { scale: 1.08; } }
}

<!-- consumer-side: full variant power the wrapper classes can't offer -->
<svg class="group-hover:animate-tc-pulse motion-reduce:animate-none">
Recommendation Register all 11 presets as --animate-tc-* tokens (keyframes move inside @theme), keep the tc-anim wrapper as the zero-config default path, and document both surfaces in the icons recipe.
Missed opportunity · Low-medium impact · NEW

Overflow-prone centering never uses -safe alignment; @source not exclusions unused

navigation/pagination.templ, nav bars (centered flex groups that clip when over-full) · examples/demo/demo.css @source glob · docs: v4.1 release notes

Two small v4.1 additions fit this codebase's safety-first character. items-center-safe / justify-center-safe fall back to start alignment when content overflows — the exact failure mode of a centered pagination row on a 375px viewport with many page numbers (the component already leans on ContainerAware for layout, but the row itself can still clip). And @source not "<path>" excludes dead directories from scanning: the demo's @source "../../**/*.templ" sweeps website/ and visualtest/ testdata into the scan for classes the demo never renders (primary-verified 2026-10-15: examples/demo/demo.css:14-15 scans "../../**/*.templ" and "../../**/*.go" — the repo-root glob reaches both). 

<!-- pagination row — center, but never clip off-canvas -->
<nav class="flex items-center-safe justify-center-safe gap-1">

/* demo.css — trim the scan root */
@source "../../**/*.templ";
@source not "../../website";
@source not "../../visualtest";
Recommendation Add -safe modifiers to the pagination/nav centering rows (visually identical at normal widths; safer at extremes), and add the two @source not lines to demo.css — the compiled artifact should not change, which the freshness guard will confirm.
Considered · Keep current approach · NEW

pointer-coarse: variant vs the centralized coarse-pointer hook block

templates/custom.css:1074 (@media (pointer: coarse)) · TestCoarsePointerCompliance · docs: v4.1 release notes

v4.1's pointer-coarse: variant could express each hover-fallback in markup (pointer-coarse:opacity-100). The repo instead centralizes the fallback in one @media block keyed by tc-* hook classes — and enforces completeness with a compliance test that knows the pattern. The centralized form is the stronger design here: one surface to audit, one test to extend, and the markup stays honest about hover-only styling. Migrating would mean rewriting the guard for zero consumer benefit.

Recommendation Keep the centralized block. Document pointer-coarse: as the escape hatch for genuinely one-off cases, the same way templ.KV is documented as the deliberate utils.Class exception.

Website docs prose is hand-styled — @tailwindcss/typography is the framework answer (verify plugin support first)

website/site.css:275+ (.docs-content h2, h3, p, ul… element rules) · docs: tailwindcss.com/docs/typography-plugin

The site's markdown-docs typography is a growing pile of scoped element rules — the classic prose use case, and v4's @plugin "@tailwindcss/typography" loads it CSS-first. Honest caveat per this repo's verify-before-adopting culture: the nix lane compiles with the standalone binary (pkgs.tailwindcss_4), and standalone support for JS plugins must be probed before adoption — the demo Docker and website CI lanes use @tailwindcss/cli, which supports plugins natively. If the standalone binary refuses @plugin, the three lanes diverge and the hand-rolled CSS stays. 

/* site.css — if and only if the standalone binary loads plugins */
@plugin "@tailwindcss/typography";
<!-- article class="prose prose-gray dark:prose-invert" replaces .docs-content rules -->
Recommendation Probe first: nix develop -c sh -c 'tailwindcss -i probe.css -o /tmp/out.css' with an @plugin line. If it compiles identically in all three lanes, migrate; otherwise keep the current CSS and note the constraint in the adoption guide.

06Conclusion

An 83/100 on a framework this deep is a strong score with an unusually short, concrete gap list — and the trajectory is the best signal: five findings from the previous audit were fixed and guard-tested within six days. The scoring components: core API and performance features 92% (weight 40%), advanced features 50% (25%), configuration 95% (15%), best-practice adherence 97% (10%), version currency 100% (10%).

The single theme of what remains: the library has mastered Tailwind as a build tool and is only beginning to use it as an extension API for consumers. @variant inside its own CSS, @utility for its helpers, @theme animate tokens, and aria-* state variants all share one property — they hand the framework's variant-composition machinery to the people who consume the library. That is where the next points live.
