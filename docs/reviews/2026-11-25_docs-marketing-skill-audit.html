00Verdict

The corpus is close to a controlled experiment: 22 consumer teams audited the same library in the same two weeks, with the same method, against pins from v1.22.0 to v1.27.0. Adoption health tracks exactly two things: whether the consumer already runs a Tailwind v4 pipeline, and whether they found the library's replacement for markup they had already hand-rolled. Both of those are communication variables, not engineering variables. Not one of the 22 reviews found a rendering bug, an accessibility regression, or a CSP hole as its headline.

What they did find, repeatedly: six different component counts (117, 124, 134, 136, 137, 138) reconciled by hand; the templ-version pairing contract met as a build break instead of a requirements row; the Tailwind coupling discovered at STACK.md time rather than README time; and hand-rolled ThemeScript/MetaRefresh/error pages sitting next to library components that exist "for exactly this" (dnsblockd's words). The AI skill, by contrast, is the corpus's ground truth: more than ten reviews cite SKILL.md by line number, and every factual correction in the corpus lands on the README, never on the skill.

The bottom line The engineering story sells itself; the number story and the first screen do not. One afternoon of README + SKILL.md work (findings D1–D4, S2–S3) deletes every recurring complaint in this corpus except the product-shaped ones, which get routed to issues, not docs.

◆What the corpus says is already excellent

Keep doing these. They are load-bearing, and two of them are the reason adoption happened at all.

SKILL.md is the fleet's most-cited library artifact 10+ reviews cite it with line numbers (audiblesync, dnsblockd, index, Cyberdom, webphone, browser-history, CV, business-networking, go-taskqueue). Zero fact corrections across 22 reviews target it. The countgen ownership works; do not weaken it.
+
Verification-as-marketing converts business-networking's review contains the paragraph that flipped SKIP→ADOPTED the same evening, and it is all maturity signals: ~1750 test functions, pixel-level visual goldens, machine-checked counts, CSP nonce auditing, ADR supervision. This is the pitch that works; lead with it.
+
The filings loop closes fast, and consumers noticed pbx-lens tracked six upstream filings (#48/#49/#50/#51/#55/#63): all closed within days, and the CHANGELOG names the consumer. cqrs-htmx, browser-history, and CV each stage upstream asks with drafts. The loop is a retention asset; make its state public and greppable (D7).
+
The Requirements section is trusted business-networking praised the README's honesty about the templ CLI + Tailwind toolchain verbatim. The honesty is there; the problem is placement and completeness (D3, D4), not tone.
+
Typed-enum positioning lands "Invalid prop states don't compile" is quoted across rejections and adoptions alike. Even the four rejections grade fit, never quality: "Rejection is fit, not quality" (google-domain-detector).

01Findings: docs (the words we publish)

Ordered by impact. Every claim cites the review that raised it; every review is <project>/docs/review/libs/templ-components.md.

Blocking · raised by 7 of 22 reviews

D1 · The component count is a guessing game

README.md:87 + README.md:108-117 · invoices, Cyberdom, index, PapDashboard, business-networking, CV, go-taskqueue, ChastityAPI, cqrs-htmx

Consumers read different numbers for the same library on the same days: 117 (go-taskqueue's counted set), 124 (README comparison table, read by invoices, index, and business-networking), 134 (Cyberdom's per-package sum), 136 (PapDashboard at v1.26.0), 137 (READMEs frozen at the release tags, verified by ChastityAPI), 138 (master README and SKILL.md). The same spread exists for enums (74 / 75 / 76) and icons (102 / 105 / 111, where go-taskqueue counted icon_names.go at the pin and webphone counted named SVGs). Packages: "11" in SKILL.md vs "19" in the README. Each audit burns paragraphs reconciling counts instead of auditing adoption; index gave up and marked the discrepancy "UNVERIFIED which is current". 

components: 117 | 124 | 134 | 136 | 137 | 138
enums:       74  | 75  | 76
icons:       102 | 105 | 111
packages:    11 (SKILL.md) vs 19 (README) · modules: "7" vs 9 go.mods

The irony is that "machine-checked counts guarded by TestDocsCountDrift" is one of the library's selling points. It is true for FEATURES.md and SKILL.md, which countgen writes. The README's headline and its comparison table are evidently outside that pipeline, and the tag-freeze lag does the rest.

Fix: one number, written by the machine, everywhere Extend countgen -w to write every count-bearing README cell, including the "By the Numbers" comparison table; print the basis inline ("138 counted components · what counts: docs/count-definitions.md"); define the icon count as names (not constants, not variants); state the module count once ("9 Go modules: 7 published + 2 repo-local"). Tag-frozen READMEs lagging master is acceptable once every number is countgen-owned.
Important · hallucination anchor

D2 · No canonical module map where skimmers look

README.md (top) · google-domain-detector, invoices, business-networking, profileagent

google-domain-detector's reviewer never loaded SKILL.md and invented the library: "root + themed, ui, base, go-htmx, demo-site, devserver", "180+ components", "~250 inline SVGs", "ECharts/chart.js bindings". All wrong. invoices read "19 packages / 7 Go modules"; business-networking counted 9 modules; profileagent said "7 core go.mods". Every consumer that miscounts the shape of the dependency mis-decides on it.

Fix: a module table above the fold One table directly under the hero: import path, what it serves, published yes/no, for each of the 9 go.mods (root + utils, icons, errorpage, htmx, datastar, charts/echarts published; visualtest + website repo-local). This is the anchor a skim-reader, a proxy page, and a reviewer agent all fall back on.
Important · caused live breakage

D3 · The templ pairing contract is buried

README.md Requirements · index, invoices, dnsblockd, CV, pbx-lens

The contract ("templ-components ≥ v1.27.0 requires templ ≥ v0.3.1100; older releases pair with templ ≤ v0.3.1070") lives in the CHANGELOG and AGENTS.md and is enforced by TestTemplVersionPin — but consumers meet it as a build break. index carried 30 broken NewAttributeExpression diagnostics from a v0.3.1020 vs v0.3.1100 skew; invoices drifted (generated v0.3.1114 vs pinned v0.3.1070); dnsblockd's bump was blocked for days and then needed a dedicated flake-input "templ-keystone" wave; CV now plans every bump as a "two-pin lockstep wave". 

templ-components ≥ v1.27.0  ↔  templ ≥ v0.3.1100
templ-components ≤ v1.26.0  ↔  templ ≤ v0.3.1070
Rule: bump both pins in one commit; regenerate all *_templ.go.
Fix: the matrix goes in README Requirements Two rows, plus one sentence: what breaks when only one side moves (generator emits symbols the pinned runtime lacks), and where the canonical bump ritual lives (release checklist / consumer guide).
Important · drives every rejection

D4 · Adoption cost is discovered at rejection time, not README time

README.md (hero) · audiblesync, io-surface, profileagent, google-domain-detector, PapDashboard

All four rejections share one reason chain: no HTTP UI surface, therefore templ codegen + Tailwind pipeline + component library = weight without return. audiblesync states the sharpest version: "the binding reason is the Tailwind chain, which has its own exclusion row… the STACK.md rationale understates the coupling". Meanwhile PapDashboard adopted icons only (score 15) and never found that docs/icons-only-adoption.md already exists.

Fix: a "what you take on" block on the first screen Under the hero: you adopt templ + a Tailwind v4 pipeline with a same-commit compiled-CSS contract; component packages ride the root module (icons/utils/errorpage adopt smaller); dark mode and CSP are built in. Link the icons-only path where consumers without a UI pipeline can see it. Honest cost up front converts "rejected with resentment" into "rejected with a trigger to revisit" — which is exactly what audiblesync recorded.
Important · adoption left on the table

D5 · Hand-rolled duplicates persist because replacements aren't where consumers look

PapDashboard, dnsblockd, invoices, journal, Cyberdom, crm

The corpus's most expensive class: PapDashboard hand-rolled a FOUC theme script + toggle that "duplicates ThemeScript exactly", plus 14 more equivalents; dnsblockd kept two hand-rolled <meta http-equiv="refresh"> tags while layout.MetaRefresh "exists for exactly this"; invoices reimplemented family→HTTP-status mapping that errorpage.ErrorHandler owns; journal kept raw <table> markup on eight pages next to DataTable; Cyberdom shipped a chat button with no pending state for up to 30 seconds while htmx.LoadingButton sat one import away. The demo's "by use case" table solves this for skill-readers; the README has no equivalent for README-readers.

Fix: "hand-rolled X? the library has Y" map A README/docs section seeded from exactly these reviews (ThemeScript, MetaRefresh, Toast, EmptyState, Pagination, DataTable, LoadingButton, errorpage, RelativeTime, LivePill), each row: the hand-roll pattern, the component, the one-line why. Refresh per release from new reviews.
Important · rediscovery tax

D7 · Known gaps live in consumers' private ledgers

CV, journal, quotaboard, browser-history, cqrs-htmx, webphone, pbx-lens

Every consumer maintains its own workarounds ledger for the same upstream gaps: CV proposes a StatCard value slot; journal needs a DataTable tfoot; quotaboard needs a day unit in CompactDuration; browser-history stages an errorpage stylesheet-slot draft; cqrs-htmx vendors a corrected popover anchor layer (Chromium 156 rejects the compound position-area values); webphone wants a Badge prefix/icon slot; pbx-lens pins four filing numbers (#48/#49/#51/#60). None of this is visible in one place, so the next consumer rediscovers each gap by hitting it.

Fix: a public upstream-requests page docs/upstream-requests.md (or a GitHub label + table): gap, requester, status, tracking issue. The CHANGELOG already names consumers; cross-link both directions. Marketing side effect: a public ledger of fast closures is itself a maturity signal.
Important · upgrade safety

D8 · Release notes omit consumer-impact lines for behavior changes

CHANGELOG.md · pbx-lens, go-taskqueue, CV, browser-history, Code-To-CV-Agent

v1.27.0 shipped a new CSP-safe validity-bridge singleton script without a nonce; under enforcing CSP the browser blocks it and native form validation silently dies. pbx-lens found it in the browser and threaded Nonce at three form sites. The same release carried a duplicated </script> wart in nine goldens. Meanwhile five reviews defer work to "the next tag" and must grep module caches or vendored trees to learn what their pin contains (pbx-lens module-cache greps, go-taskqueue vendored counts, Code-To-CV-Agent's pseudo-pin).

Fix: "Consumer impact" line per entry + pin lookup Every CHANGELOG entry that changes rendered markup, script emission, or requirements gains one "Consumer impact:" line. Promote docs/version-support.md ("what's in YOUR pin") into the README next to the count block.
Nice to have · five reinvented wheels

D6 · Five consumers rebuilt the same CSS-drift guard

CV, dnsblockd, quotaboard, cqrs-htmx, Code-To-CV-Agent

The same-commit compiled-CSS contract is the hardest part of adoption, so consumers engineer their own enforcement: CV's gen-tc-safelist.sh + fresh-clone golden + --check-at-pin gate; dnsblockd's regen-ui byte-equity check; quotaboard's corpus-fresh flake check; cqrs-htmx's check-css-bundles; Code-To-CV-Agent's "gotcha 24" app.css rebuild rule. Five independent solutions to one shared problem, none canonical.

Fix: publish the guard recipe One docs page with the canonical CI recipe (rebuild → diff → fail) and the tc doctor CSS-freshness wiring, linked from the consumer guide's compiled-CSS rule. Consumers upgrade from hand-rolled guards to the shared one at leisure.

02Findings: marketing (how the library sells itself)

Important · invisible assets

M1 · The demo site and the theme presets are invisible to the corpus

README.md · 0 of 22 reviews mention either

Not one review references templcomponents.lars.software or the four theme presets (default, minimal, glass, emerald). That matters because the two unhappiest adoptions in the corpus are aesthetic mismatches: PapDashboard's "industrial" freeze (icons only, score 15) and ChastityAPI's token-language conflicts (library gray-* defaults vs its --color-tc-* system, which killed DataTable and ValidationSummary adoption). Presets and the "remap, don't replace" @theme recipe are the existing answer, and the consumers that needed them most never saw them.

Fix: surface theming assets where objections form Link the demo and the presets from the README's theming section; add a two-sentence "strong custom aesthetic? start from a preset or remap via @theme" note with a link to the recipe.
Important · cadence risk

M2 · The release train lags demand, and one consumer went to pseudo-versions

go-taskqueue, CV, browser-history, pbx-lens, Code-To-CV-Agent

At review time the checkout ran 87–91 unreleased commits past v1.27.0, and consumers kept gating work on "the next tag": go-taskqueue's CopyButton fix, CV's doctor false-alarm fixes, pbx-lens's six closed filings. Code-To-CV-Agent went further and pinned the pseudo-version v1.27.1-0.20261106105459-2e16bcaf642b to get unreleased fixes — the riskiest possible pin (it re-resolves on every upstream push) and a direct measure of tag-lag demand.

Fix: cut minors faster, or publish rc tags Either shorten the wave-to-release cycle when [Unreleased] carries consumer-tracked fixes, or tag -rc previews so consumers can pin something real. Document the train policy so "waiting for the tag" has a known answer.
Nice to have · keep the winner

M3 · Lead with verification, with current numbers

README.md (hero) · business-networking's flip paragraph is the template

The one review that flipped from SKIP to ADOPTED mid-audit did so on maturity signals, not features. The README should keep those signals on the first screen with fresh, countgen-fed numbers: test functions, guard tests, golden counts, the tc doctor/tc lint scanner story, ADR count. The scanner story also deserves its own beat: CV's two tc doctor false alarms were fixed upstream (issue #35), which is exactly the "we close feedback fast" narrative.

Baseline: the skill works It is the corpus's most-cited artifact, it is countgen-written and drift-guarded, and reviews that loaded it reached correct verdicts 21 times out of 22. The improvements below are additions, not repairs.
Important · absorb the private canons

S4 · Harvest the fleet's recurring gotchas into the consumer guide

references/consumer-guide.md · Code-To-CV-Agent, CV, dnsblockd, cqrs-htmx, journal

Consumers maintain private gotcha canons for problems this repo already knows about: Code-To-CV-Agent's "gotchas 24/32/42" (same-commit CSS rebuild, paired bumps, explicit BaseProps.ID for deterministic pages), CV's docs/agents/templ-ui.md adoption table + safelist ritual, dnsblockd's adoption map, cqrs-htmx's ADR-0053 divergences, journal's F44–46 table law. Each is a doc failure one level up: the consumer guide should own the recurring ones so the next consumer doesn't write gotcha 43.

Fix: add the five recurring gotchas Explicit IDs vs EnsureID randomness (render determinism/ETags); same-commit CSS rebuild; nonce requirement for every new singleton script; the amber warning-hue semantic change; the paired templ bump. Each with a repro and the guard that catches it.
Nice to have · reviews reinvented it 4 times

S2 · Add a "what's in my pin?" protocol to consumer essentials

SKILL.md consumer essentials · pbx-lens, go-taskqueue, CV, Code-To-CV-Agent

Four reviews independently built the same lookup: grep the module cache at the pinned version, count the vendored tree, search the CHANGELOG for the closing commit, then conclude "closed post-tag, workaround stays". The catalogue already says it tracks the source tree ahead of pins; what's missing is the five-line protocol for answering "does MY pin have X?".

Nice to have · faster correct verdicts

S3 · Add the adopt/reject quick profile

SKILL.md (top) · audiblesync, io-surface, profileagent, google-domain-detector, PapDashboard

Five of 22 verdicts share one shape: needs a served UI + templ CLI + Tailwind v4 pipeline; icons-only is the escape hatch; plain-templ without Tailwind is a likely reject with a named trigger. Putting that profile in the skill's first screen lets a reviewer agent reach the audiblesync-quality verdict (rejection with revisit triggers) in one read — and links docs/icons-only-adoption.md for the PapDashboard case, which currently surfaces at score 15 instead of as a documented path.
