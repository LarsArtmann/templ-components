The Color Domain Model

One concept — “why is this thing colored” — is modeled thirteen different ways in this library: 10 enums, 12 lookup maps, 3 palette slices, ~10 fixed-color sites, 52 CSS tokens nobody emits, and 2 guard regexes with a stale hue list. This is the deep dive into that fragmentation and the typed model that collapses it.

Companion reports

This extends 2026-07-18 data-model-review (which concluded “typed enums everywhere — the Props model is a good fit”) and 2026-10-14 50-big-picture-ideas. The prior verdict was correct locally: every component’s enum is well-formed. The finding here is global: the color subdomain has no shared language between those well-formed islands. It also slots the Go layer into ADR-0044’s CSS-token plan (T1, v2-gated) without contradicting its rejected options.

01Problem Catalog

C2 — Critical · The class layer is stringly typed everywhere

1,880 raw color-utility occurrences (233 unique tokens, 14 hue families) flow through free-form strings. Nine props fields accept color-ish strings with no type, no validation, silent failure: Spinner.Color, ProgressBar.Color, CircularProgress.Color/TrackColor, SegmentBarSegment.Color (“a full class pair”), BarChartBar.Color, LineChartSeries.Color, PieChartSlice.Color, HeatmapProps.ColorVar. A typo like "bg-emerald-6oo" compiles, passes every test, and renders the browser default — the contract lives only in doc comments.

H1 — High · Six hand-maintained “green = success” recipes

The same semantic decision — success is green, light 500-ish, dark 400-ish — is re-encoded per component, each with its own shade arithmetic:

The per-surface differences are legitimate design (a dot needs a solid, an alert needs a tint). The problem is that the relationship between those surfaces is maintained by parallel editing — seven places must agree when the recipe changes, and nothing links them.

H2 — High · Hue names frozen into the public API

StatToneBlue = "blue" and KanbanToneGreen = "green" encode an implementation detail (which Tailwind hue) into the permanent v1/v2 contract. After ADR-0044’s T1 swap the accent family is accent-*, not blue — the enum value will still say “blue”. The inverse inversion exists too: statusToBadgeMap keys on the color words "green"/"red"/"yellow"/"blue" as status semantics — the consumer’s domain language mapped through color names.

H3 — High · The light/dark invariant lives in a regex, not the model

“Every color needs a dark: sibling” is enforced by TestDarkModeCompliance/TestDarkModeSemanticColors — a source-text regex scan (utils/darkmode_scan.go). The model cannot express the pairing, so 669 dark: occurrences are hand-maintained and policed after the fact. Worse, the semantic regex’s hue list is a stale copy of the palette: it knows bg-(blue|red|green|amber|orange|gray) and five text hues — emerald, rose, violet, cyan, pink, purple and bg-yellow escape the semantic scan entirely (darkmode_scan.go:112-114). The charts currently carry correct pairs, but a dropped dark: in any of those seven hues would ship silently.

H4 — High · Four unlinked representations of one concept

“The library’s danger color” exists simultaneously as: (1) Go lookup maps (12 of them), (2) emitted Tailwind classes, (3) 52 --color-tc-* token definitions in templ-components-theme.css — shade-complete since 2026-10-10, yet emitted by zero components (ADR-0008 stays opt-in), and (4) the hand-maintained “Which colors does the library use?” table in docs/recipes/theme-bridge.md. Five if you count the guard regexes. None can reference another; every change is a five-place edit.

M1 — Medium · Runtime validation masquerading as type safety

PageProps.ThemeColor/DarkThemeColor are raw strings validated at render time by the validHexColor regex (layout/base.templ:13-24). HeatmapProps.ColorVar is a two-variable protocol smuggled through one string: pass "--ds-brand" and the component synthesizes rgba(var(--ds-brand-rgb), n) (heatmap.go:140-144) — the required -rgb triplet sibling is documented nowhere in the type system and fails silently as an invisible heatmap.

M2 — Medium · ButtonType couples two axes

ButtonPrimary…ButtonGhost (hierarchy/variant axis) and ButtonOutlineDanger/Warning/Success/Info (color axis) live in one 9-value enum. The cross product is already leaking — there is no ButtonOutlinePrimary — and every new variant multiplies: the enum grows variant×color instead of composing them.

M3 — Medium · Fixed-color sites with no derivation channel

StepIndicator state colors, CountBadge (bg-red-600 dark:bg-red-500), ValidationSummary’s red set, ConfirmDelete, ProgressBar/CircularProgress defaults, the echarts bridge’s five hardcoded gray hex pairs (dark_mode_bridge.go:21-29) — all semantic colors with no tone type and no token reference. They cannot be re-skinned by any mechanism short of editing the library.

Severity roll-up

Critical

C1 · The color subdomain has no shared type

display/* · feedback/styles.go · errorpage/styles.go · charts

Thirteen vocabularies, four spellings of “error”, six green recipes — every symptom in C2/H1/H2/H4 is this one root cause: the concept “color intent” was never modeled once, so every component re-modeled it locally.

Fix One canonical tone.Tone (semantic) + tone.Hue (categorical) pair in a leaf package; every existing enum derives from it via adapter methods; v2 collapses the duplicates (ADR-0006 alias-then-remove precedent).
Critical

C2 · Color strings cross the API boundary untyped

LineChartSeries.Color · SegmentBarSegment.Color · Spinner.Color · ThemeColor · ColorVar · +4 more

Nine props fields take free-form class/hex/CSS-var strings. The failure mode is silent: an unknown class emits verbatim and renders the browser default; a bad hex fails a render-time regex; a missing -rgb sibling var makes the heatmap invisible.

Fix Typed ChartColor constants (untyped literals keep compiling — non-breaking), branded HexColor with a validating constructor, and a documented single-token contract for ColorVar.
Important

H3 · The guard regex is a stale copy of the palette

utils/darkmode_scan.go:104-114

The dark-mode guard’s semantic hue list covers 6 bg / 5 text hues; the library also uses emerald, rose, violet, cyan, pink, purple, and bg-yellow (charts, kanban, stat tiles). Those escape the scan. The model is invisible to the type system, so the guard guesses — and the guess drifts.

Fix Derive the scanned hue list from the tone/hue tables (single source); longer term the Pair type makes the light/dark coupling structural and the library-side regex retires.
Nice to have

M3 · Fixed-color sites are unreachable by theming

StepIndicator · CountBadge · ValidationSummary · echarts bridge

These sites accept no tone, no token, no override — they are correct today and un-skinnable forever. Routing them through the tone table (or at minimum the tc-* opt-in layer) costs one line each once the table exists.

What the model gets right

Fairness first: the 2026-07-18 review’s verdict stands locally. The right raw material for the redesign is already in the codebase.

+
ADR-0006 is the proof the unification pattern works AlertType + ToastType collapsed into one FeedbackType with shared generic lookup — aliases removed at v2. The redesign is this pattern applied to the whole color subdomain, not a new invention.
+
errorpage.Family is the best-modeled color consumer A real domain concept (rejection/conflict/transient/…) with one 10-field visual set per family, single map, single accessor. It shows the library already knows how to separate domain from visual — it just did it once, for errors only.
+
feedbackStyleSet is the right shared-shape Border/BG/Text/Icon resolved once for Alert + Toast + the JS mirror (toastJSStyles derives from the same map — zero drift). Generalize this struct, don’t replace it.
+
chartColor* constants already single-source three palettes line/pie palettes are literal constants in one file; SegmentBar duplicates them as bg-* twins only because the scanner demands complete literals — a table with two literal columns absorbs that duplication honestly.
+
ADR-0044/0008 already own the CSS half and rejected the right things The accent token family (v2), the shade-complete opt-in tc-* layer, and the explicit rejection of per-component Color props (option D) are all correct. This report adds the missing Go half and changes none of those decisions.
+
Render-time fallback discipline Unknown enum → documented fallback, never a panic (zero-runtime-panic guard). The redesign keeps this: invalid input degrades to neutral, the type system just makes valid input the easy path.

02The Vision

What perfection looks like

1. One word per intent — a consumer says tone.Danger and every component (Badge, Alert, Toast, StatusDot, Button outline, Scrollback) renders its danger treatment. 2. Hues are data-viz vocabulary — categorical series colors — never status semantics. 3. The green recipe is chosen exactly once, in one table, and every surface (dot, tint, text, border, ring, icon) derives from it. 4. The light/dair pairing is structural — a value of type Pair that cannot exist with only one half. 5. The guard regexes, the docs color table, and the CSS token inventory are all generated from that one table — five hand-maintained representations become one. 6. The library’s standing theming decision survives untouched: values still come from CSS (@theme / tc-* tokens); Go owns the intent vocabulary only.

03The Go Data Model

utils/tone — the leaf package every module may import

utils is already the DAG leaf (root packages, feedback, errorpage, charts all import it) — the only home the import graph permits. 

// Package tone is the library's canonical color-intent vocabulary.
// Two orthogonal axes, because the current code proves they ARE orthogonal:
// status semantics (success/danger/…) and categorical identity (chart series).
package tone

// Tone answers "WHY is this colored?" — one word per intent.
type Tone string

const (
	ToneNeutral Tone = "neutral" // absence of signal
	ToneSuccess Tone = "success" // goal reached, healthy
	ToneWarning Tone = "warning" // attention, degraded
	ToneDanger  Tone = "danger"  // failure, destructive
	ToneInfo    Tone = "info"    // neutral-active, in progress
	ToneAccent  Tone = "accent"  // brand axis (ADR-0044)
)

func (t Tone) IsValid() bool { return contains(allTones, t) } // THE one IsValid

// Hue answers "WHICH categorical color?" — data-viz and decoration only.
type Hue string

const (
	HueBlue Hue = "blue"; HueEmerald Hue = "emerald"; HueAmber Hue = "amber"
	HueRose Hue = "rose"; HueViolet Hue = "violet"; HueCyan Hue = "cyan"
	HueOrange Hue = "orange"; HuePink Hue = "pink"; HuePurple Hue = "purple"
	HueGray Hue = "gray"
)

Pair — the light/dark coupling becomes structural

Both fields are complete literals including the variant prefix — the Tailwind scanner (and the ADR-0045 shipped class corpus) sees every candidate; joining them at runtime is a plain space join of complete tokens, which is safe. 

// Pair couples a light utility with its dark sibling. The dark half carries
// its own variant prefix so both are scanner-visible complete literals.
type Pair struct {
	Light string // "bg-green-500"
	Dark  string // "dark:bg-green-400"
}

func (p Pair) Classes() string { return p.Light + " " + p.Dark }

The one table — tone × surface, chosen once

This generalizes feedbackStyleSet (Border/BG/Text/Icon) from one package to the whole library. Every component’s map becomes a one-line view of this table. 

// Surfaces is what a tone looks like on every surface the library paints.
// THE only place a shade is chosen by hand.
type Surfaces struct {
	Dot      Pair // solid dot: StatusDot, Kanban, Avatar, Badge dot
	Text     Pair // strong text on plain background
	TextSoft Pair // readable text on the tint
	Border   Pair // hairline for tinted containers
	BGTint   Pair // washed container: badges, alerts, tiles
	BGSolid  Pair // solid fill: primary buttons, bars
	Icon     Pair // icon-only accent
	Ring     Pair // focus rings
}

var styles = map[Tone]Surfaces{
	ToneSuccess: {
		Dot:      Pair{"bg-green-500", "dark:bg-green-400"},
		BGTint:   Pair{"bg-green-50", "dark:bg-green-900/20"},
		Text:     Pair{"text-green-700", "dark:text-green-400"},
		TextSoft: Pair{"text-green-800", "dark:text-green-200"},
		Border:   Pair{"border-green-200", "dark:border-green-800"},
		Icon:     Pair{"text-green-600", "dark:text-green-400"},
		// …
	},
	// neutral, warning, danger, info, accent — five more entries,
	// and NOTHING else in the library hand-picks a status shade again.
}

func Style(t Tone) Surfaces { return utils.Lookup(styles, t, styles[ToneNeutral]) }

Charts — one hue table, two literal columns

Absorbs the three palette slices AND SegmentBar’s forced bg-* duplication: one row per hue, both spellings side by side. ChartColor stays a string type so existing untyped literals keep compiling — non-breaking. 

type ChartColor string // complete literal pair, or a constant below

const (
	ChartBlue   ChartColor = "text-blue-600 dark:text-blue-400"
	ChartEmerald ChartColor = "text-emerald-600 dark:text-emerald-400"
	// … 6 more, replacing chartColor* + 3 palette slices
)

type LineChartSeries struct {
	// Color overrides the palette. Takes a ChartColor constant
	// (display.ChartEmerald); raw literals still compile.
	Color ChartColor

05Validation Layer

How invalid states become unrepresentable

Closed sets: Tone/Hue are string enums with ONE IsValid and ONE exhaustiveness test — replacing ten per-enum IsValid copies and their drift-guarded test counts. Table completeness: one test asserts every tone has a Surfaces entry and every Surfaces field has both Pair halves with the dark: prefix present — the invariant the 1,880-site regex scan enforces today, checked at ONE definition site instead. Boundary validation: ParseHexColor validates once at construction; PageProps takes HexColor, the render-time regex retires. Render safety preserved: unknown tone → neutral fallback inside Style() — a bad value can never crash a page render (the library’s standing graceful-degradation rule). Scanner safety: every class the table emits is a complete literal inside the package — the ADR-0045 class corpus picks them up; nothing is concatenated from parts.

Where color knowledge lives — before vs after

today: ~28 encodings ├── 10 enums · 12 class maps/palettes · 8 hue consts · 2 KV branch clusters ├── ~10 fixed-color sites (StepIndicator, CountBadge, echarts hex …) ├── 52 tc-* CSS tokens defined, emitted by 0 components ├── 2 guard regexes with a stale hue list └── 1 hand-maintained docs table (theme-bridge.md)
after: 1 source ├── utils/tone: 2 axes · 2 tables (tone×surface, hue×utility) ├── generated: guard hue list · docs color table · tc-token inventory └── CSS keeps owning VALUES (@theme / ADR-0044) — unchanged

06Decision Log

#DecisionRejected alternative — why
D1 Home the vocabulary in utils/tone display-owned: feedback/errorpage importing display violates the import DAG. New top-level module: the 7-module split is frozen (ADR-0034/0040).
D2 Word: Tone + Hue “Color” lies (it’s intent, not a color); “Severity” fits only the feedback subset. Five of ten existing enums already end in Tone — extracting the language the code already speaks.
D3 Canonical danger spelling: danger; FeedbackError becomes a v2-removed alias Keeping error: error is an event/domain concept, danger is the presentation intent — and StatusTone/ButtonType/ScrollbackTone already say danger. ADR-0006/0022 is the exact alias-then-remove precedent.
D4 Two axes: semantic Tone vs categorical Hue Forcing semantics onto StatTone/KanbanTone: a purple kanban column is not “info” — categorical identity is a real, different concept (charts prove it daily).
D5 Adapters now, collapse at v2 Big-bang rename: breaks 100% of consumers for zero visual gain; ADR-0039 already batches breaking changes at v2 with ADR-0044 T1.
D6 No new per-component color props That’s ADR-0044 option D, explicitly rejected — CSS tokens own values. Go owns the intent vocabulary; the enum IS the color channel.
D7 Pair fields carry complete literals (dark: prefix included) Storing bare "bg-green-400" and synthesizing dark: at runtime: the scanner can’t see the variant token — CSS never generated (repo rule).
D8 statusToBadgeMap raw-string keys stay They are the consumer domain’s status language, not the library’s color language — a deliberate translation layer, already overridable via StatusBadgeMapper. Document it as such.
D9 ButtonType axis-split deferred Real coupling (M2) but orthogonal to the color model; a v2+ composition (Variant × Tone) noted for the backlog, not smuggled into this redesign.

07Anti-Patterns

Traps to avoid while adopting

1. Never name a public tone value after a hue. StatToneBlue is the cautionary tale — the value outlives the palette choice. 2. Never copy a shade recipe between components — if two components need “green text on green tint”, that’s a Surfaces column, not a new map entry. 3. Never widen the dark-mode regex by hand — the hue list must be derived from the tone/hue tables or it drifts again (H3 happened exactly this way). 4. Never accept a raw class string where a Tone/Hue/ChartColor exists — the escape hatch is for literals, not API design. 5. Never concatenate variant prefixes at runtime (D7). 6. Never break the struct-literal zero-value contract — StatCardProps{} must render the documented blue tile; the Hue zero value carries that default. 7. Never let the tone table import a component package — utils/tone stays a leaf or the DAG closes a cycle.

08Migration Roadmap

1

Phase 0 — v1.x: land utils/tone (zero visual change, zero breakage)

Tone + Hue types, the two tables, Pair; adapter methods on the ten existing enums. New components are tone-ready (extends ADR-0044’s token-ready rule). One IsValid, one exhaustiveness test; counts guards updated in the same commit.

2

Phase 1 — v1.x: type the stringly boundaries

Export ChartColor constants; type the nine Color fields (untyped literals keep compiling); HexColor constructor for PageProps; document the ColorVar -rgb contract. Derive the dark-scan hue list from the tables — the stale-regex hole (H3) closes immediately.

3

Phase 2 — v2, batched with ADR-0044 T1: the collapse

Enums become aliases of tone.Tone/tone.Hue then vanish (ADR-0006 pattern); FeedbackError→Danger rename; per-component maps deleted, maps become table views; components emit accent-*/tc-* classes per ADR-0044; feedbackStyleSet demoted to a view. Full golden + visual rebaseline (pixels expected identical — defaults unchanged), demo CSS recompile, CHANGELOG.

4

Phase 3 — post-v2 probe: retire the dark: pairs

669 hand-maintained dark: occurrences could collapse into token-level mode flipping (@theme inline + .dark {} overrides). Requires a probe against the pinned Tailwind 4.3.3 binary (repo rule: probe, never assume) and a deliberate visual rebaseline. Big win, independently shippable.

5

Phase 4 — generated everything

theme-bridge.md’s color table, the tc-token inventory check, and the guard hue list all generated from utils/tone (docs-count drift-guard style). Five hand-maintained representations of “the library’s colors” become one.

09Conclusion

“The library never had a color problem — it had thirteen local solutions to one modeling omission. Every component modeled color correctly in isolation and differently in public. Extract the language the code already speaks — tone and hue — and 1,880 string occurrences, six green recipes, four error spellings, and two stale regexes all become views of two small tables.”
