## e) WHAT WE SHOULD IMPROVE

1. **Treat Visual-Regression red as environment-first when the failing route SET changes between runs.** Disjoint sets + sub-0.4% margins = runner drift, not content. A one-paragraph decision rule in `docs/visual-testing.md` would have saved the wrong prediction (d1) and the pre-release misdiagnosis.
2. **Pin the Visual CI job's environment** (runner image version or a contained re-baseline ritual) so ubuntu image migrations can't silently invalidate the whole route-golden corpus. The migration annotation was visible in the failing runs.
3. **Release-checklist addition:** "if remote master is red and the fix is on local master, push-then-tag in ONE push is acceptable ONLY for lanes whose redness the local run provably fixes — and say WHICH lanes you expect to flip." I did this reasoning; it should be written down with the outcome (partially right, Visual wrong).
4. **Auto-decline policy for the templ-bump dependabot PRs** (they fail CI by design; each one costs a CI cycle and attention).
5. **Drain background jobs before context switches** (d2).
6. **Single-writer × release-watch:** when a sibling is mid-work, defer tree-mutating watch steps (tidy sweep) and say so in the report — worked this time; make it the explicit rule.
7. **Checklist item order:** the `gh run list` master-green check worked well as a FIRST pre-flight command — keep it literally first, with the route-set comparison against the last failure.
